# Plugin Pack Specification v1

> This doc defines the file structure, manifest spec, signing mechanism, and distribution flow of a plugin pack.

---

## 1. Pack File Structure

A plugin pack is a `.tgz` archive that must contain a top-level directory, with `manifest.json` and at least one resource-layer directory inside.

```
my-plugin-1.0.0.tgz
└── my-plugin/
    ├── manifest.json          # required - pack metadata
    ├── mcp/                   # optional - MCP Server declarations
    │   └── *.json
    ├── tools/                 # optional - tool declarations
    │   └── *.json
    ├── experts/               # optional - Expert declarations
    │   └── *.json
    └── skills/                # optional - Skill declarations
        ├── *.json
        └── *.md               # Skill external Markdown files
```

**Constraints**:
- The archive must contain exactly one top-level directory
- `manifest.json` must be at the top-level directory root
- At least one resource-layer directory (mcp / tools / experts / skills) must contain at least one `.json` file
- The `skills/` directory additionally allows `.md` files (as Skill external content files)

## 2. manifest.json Spec

### 2.1 Field Definitions

| Field | Type | Required | Description |
|------|------|------|------|
| `id` | `string` | Yes | Plugin unique identifier, `{scope}.{name}` format, e.g. `acme.support` |
| `name` | `string` | Yes | Human-readable name |
| `version` | `string` | Yes | Semantic version, follows semver |
| `description` | `string` | No | Plugin description |
| `author` | `string` | No | Author name |
| `signature` | `string` | No | HMAC-SHA256 signature (base64), auto-generated by the packer |
| `signedAt` | `string` | No | Signing time (ISO 8601), auto-generated by the packer |

### 2.2 Example

```json
{
  "id": "acme.support",
  "name": "ACME Support Plugin",
  "version": "1.0.0",
  "description": "Customer support expert and tools for ACME Corp",
  "author": "ACME Engineering",
  "experts": [
    {
      "id": "acme.support-agent",
      "label": "Support Agent",
      "description": "Handles customer support queries",
      "tools": ["acme-ticket-lookup", "acme-create-ticket"],
      "skills": ["acme.reply-tone"]
    }
  ],
  "skills": [
    {
      "id": "acme.reply-tone",
      "label": "Reply Tone",
      "content": "Reply to customers in a friendly, professional tone."
    }
  ],
  "tools": [
    {
      "name": "acme-ticket-lookup",
      "kind": "http",
      "label": "Ticket Lookup",
      "category": "mcp-industry",
      "description": "Search ACME support tickets"
    }
  ],
  "mcp": [
    {
      "id": "acme-mcp",
      "transport": "sse",
      "url": "https://mcp.acme.example.com/sse"
    }
  ]
}
```

## 3. Signing Mechanism

### 3.1 Algorithm

Uses **HMAC-SHA256** to sign the pack content.

### 3.2 Signing Flow

1. Iterate all files in the plugin directory, sorted by relative path lexicographically
2. For each file, feed `relativePath\0fileContent` into HMAC
3. If the file is `manifest.json`, remove the `signature` / `signedAt` fields before computing
4. Compute the final digest with HMAC-SHA256 and the signing key (base64 encoded)
5. Write the digest and signing time into `manifest.json`'s `signature` and `signedAt` fields
6. Pack the directory as `.tgz`

**Design decision**: signing is based on file content, not tgz bytes, because gzip compression is non-deterministic (depends on timestamp, platform); identical content produces different bytes across environments. Content-based signing guarantees cross-platform reproducibility.

### 3.3 Key Management

| Environment | Key source | Note |
|------|----------|------|
| Dev | `PLUGIN_SIGN_KEY` env var | local dev/test |
| CI/CD | CI Secret | automated pack pipeline |
| Production | key management service | official release signing |

**Key format**: any UTF-8 string; a random string of 32+ bytes recommended.

### 3.4 Verification Flow

1. Extract the `.tgz` archive
2. Read `signature` and `signedAt` from `manifest.json`
3. Recompute the HMAC from directory file contents (auto-excludes manifest signature / signedAt)
4. Compare the result with the `signature` field
5. Check `signedAt` is within an acceptable time window (default 90 days)

### 3.5 Security Constraints

- On signature verification failure, the install must abort with an error
- Packs without a `signature` field can be installed but emit a warning (unsigned packs allowed for dev)
- Packs with `signedAt` older than 90 days require an explicit `--force` flag to install

## 4. Pack Command

### 4.1 Basic Usage

```bash
pnpm plugin:pack --dir <pack-directory> [--out <file.tgz>]
```

### 4.2 Signed Pack

```bash
PLUGIN_SIGN_KEY=<secret> pnpm plugin:pack --dir <pack-directory> [--out <file.tgz>]
```

When `PLUGIN_SIGN_KEY` is present, the packer signs automatically.

### 4.3 Parameters

| Param | Required | Default | Description |
|------|------|--------|------|
| `--dir` | Yes | - | plugin pack directory path |
| `--out` | No | `dist/<name>-<timestamp>.tgz` | output file path |

---

## 5. Install Command

### 5.1 Basic Usage

```bash
pnpm plugin:install --file <pack.tgz> [--tenant <tenantId>]
```

### 5.2 Verify Signature on Install

```bash
PLUGIN_SIGN_KEY=<secret> pnpm plugin:install --file <pack.tgz>
```

When `PLUGIN_SIGN_KEY` is present, the installer verifies the signature.

### 5.3 Force Install (skip time check)

```bash
pnpm plugin:install --file <pack.tgz> --force
```

### 5.4 Parameters

| Param | Required | Default | Description |
|------|------|--------|------|
| `--file` | Yes | - | `.tgz` archive path |
| `--tenant` | No | `local` | target tenant ID |
| `--force` | No | `false` | skip signature time-window check |
