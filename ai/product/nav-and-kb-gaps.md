# 信息架构与知识库 — 现有不足与调整原则

> **状态:** **已关闭**（主路由收敛 + 双语原则 + 验收齐）  
> 最后更新：**2026-09-05**  
> 背景：对照市面知识库方案、双引擎能力与 AI App 路由现状，收敛产品主路径与中英文表述。  
> 相关：[platform.md](../platform.md) · [design/rag.md](../design/rag.md) · [app/routing.md](../app/routing.md) · [workflow-terminology.md](./workflow-terminology.md) · **[kb-and-monitor-ux-plan.md](./kb-and-monitor-ux-plan.md)**（知识库重做 + 监控并入运行时）

## 一、总原则（已拍板）

| 原则 | 说明 |
|------|------|
| 主路由极简 | 顶导**只保留**「对话」与「工作流」；其余进设置下拉 |
| 双语分离 | 明确 **zh-CN / en-US** 两套文案；中文界面**不得**出现 Agent、RAG、MCP 等英文产品词 |
| 知识库定位 | 产品知识库 = **平台资产知识**（Schema / Flow 为主），不是通用文档中台，也不是 Seekstone |
| Seekstone | 仅研发文档外脑，**不上产品**、不替代 `/rag` |

命名对照：

| 中文（zh-CN） | 英文（en-US） | 路由 |
|---------------|---------------|------|
| 对话 | Chat | `/` |
| 工作流 | Workflow | `/workflows` |

> 口语中的「对话 / workflow / chat」统一映射为上表两支柱：中文说「对话 + 工作流」，英文说「Chat + Workflow」。

## 二、不足分块整理

### 2.1 信息架构（路由与导航）

| 不足 | 现状 | 影响 |
|------|------|------|
| 主路径过载 | 顶导同时露出对话、工作流、知识库、插件、监控等 | 建设者工具与终端使用面混在一起，主叙事不清 |
| 能力页与消费页同级 | RAG / 插件 / MCP / 评测 / 调试与对话、工作流并列 | 用户以为「产品 = 一堆运维页」，而非「对话驱动 + 工作流编排」 |
| 文档与 UI 术语漂移 | 文档写 Agent 编排 / Chat LangGraph，UI 中英混用 | 中文用户看到 Agent，认知成本高 |
| 次要能力无归属 | 集成、密钥、调度、评测散落 | 找不到「设置」心智，又占主路由 |

**调整**：主路由仅「对话」「工作流」；知识库 / 插件 / 监控 / 模型 / 记忆 / 集成 / 评测 / 调试等收入设置分组。路由本身可保留，**不删能力，只降导航权重**。

---

### 2.2 国际化与文案

| 不足 | 现状 | 影响 |
|------|------|------|
| 中文夹英文产品词 | 「Agent 编排」「RAG 知识库」「MCP 管理」「AI 对话」 | 违反「中文版应全是中文」 |
| 英中各说各话 | 英文仍 Agent Workflows，中文未对齐工作流 | 双语切换后心智不一致 |
| 硬编码中文未走 i18n | 部分组件（如产物回传）写死「Agent」 | 切语言无效，且污染中文 UI |
| 术语表未强制进 UI | `workflow-terminology` 有定义，布局未强制引用 | 文档正确、界面仍旧 |

**调整原则**：

- zh-CN：对话、工作流、知识库、插件中心、工具服务（原 MCP）、嵌入模型、检索调试…  
- en-US：Chat、Workflow、Knowledge、Plugins、Tool Services…  
- 内部代码名（`agentWorkflow`、`rag__search`）可保留英文；**用户可见字符串必须本地化**。

---

### 2.3 产品知识库（相对市面方案）

| 不足 | 现状 | 相对市面 |
|------|------|----------|
| 定位未对外说清 | 实现已是 Schema/Flow 资产索引 + 文档辅线 | 易被当成「又一个 Dify 式文档库」 |
| 通用文档 KB 体验薄 | 有 document 入库与切片，但非主叙事 | 输给 Dify / Coze / 企业知识中台 |
| 企业治理弱 | 多源同步、细粒度权限、引用溯源、审计不足 | 企业采购常卡在治理而非召回率 |
| 资产闭环未产品化讲透 | ~~有覆盖率 / stale / 重建，运营叙事弱~~ **已补**：待补齐含表单/流程/过期清单可操作 | 「表单/流程即知识」差异化未形成卖点 |
| 成功指标偏工程 | 有三路检索调试，缺业务 KPI（复用率、改表成功率） | 难证明知识库「有用」 |

**不该下的功夫**：用 Seekstone 冒充产品知识库；与通用 RAG 拼切片算法军备。

**该下的功夫**：

1. 资产知识闭环（变更 → 索引 → 过期 → 覆盖率可运营）  
2. 领域切片质量（field / node 是否真助复用）  
3. 对话 / 工作流消费质量（命中后是否少胡编、能改表改流）  
4. 再评估是否做「第二曲线」通用文档库（权限 / 多库 / 溯源）

---

### 2.4 知识体系混淆（三类库未拆开）

| 类型 | 应有职责 | 当前问题 |
|------|----------|----------|
| ① 资产知识 | Schema / Flow 结构化索引，服务专家与工作流 | 与「上传文档问答」叙事混谈 |
| ② 业务文档知识 | 制度 / FAQ / 合同等 | 能力有、产品位次不清 |
| ③ 研发知识（Seekstone） | 设计/PRD/架构，仅内部 | 易被误认为产品方案一部分 |

**原则**：文档与排期必须标明改的是 ① / ② / ③ 哪一层；禁止用 ③ 的工具链替代 ① 的产品建设。

---

### 2.5 对话 × 工作流消费面

| 不足 | 现状 | 影响 |
|------|------|------|
| 双引擎对用户不透明 | LangGraph 默认对话 vs 绑定已发布工作流 | 用户不知何时在「对话」、何时在「跑工作流」 |
| 自动建专家缺失 | 专家靠 JSON / 插件中心 | 相对 Coze「描述即 Bot」缺口大 |
| 发布消费面弱 | 缺商店 / 轻量公开助手页 / 渠道 | 建设者强、终端分发弱 |

（与竞品差距详见会话分析；此处只记产品不足，不重复全表。）

---

### 2.6 编排广度（非主路径，记缺口）

| 不足 | 说明 |
|------|------|
| 横向节点偏少 | Iteration / Code 等通用零件厚度不如 Dify |
| 调试深度 | 执行详情有；单步断点明确不做 |
| 自定义专家进任务链 | `legacyAgentKey` 五槽限制，一等公民不足 |

主路由收敛后，这些仍属设置/建设者能力，不挤占「对话 / 工作流」心智。

## 三、导航落地规格

### 3.1 主路由（顶导）

| 顺序 | zh-CN | en-US | path | 高亮规则 |
|------|-------|-------|------|----------|
| 1 | 对话 | Chat | `/` | `path === '/'` |
| 2 | 工作流 | Workflow | `/workflows` | `/workflows*`、`/executions*` |

### 3.2 设置下拉（保留能力，降权）

| 分组 zh | 分组 en | 原主路由/设置项 |
|---------|---------|-----------------|
| 配置 | Config | 知识库、插件中心、用量与成本、模型、嵌入模型、模板、长程记忆 |
| 集成 | Integration | 集成测试、集成密钥、工具服务（原 MCP） |
| 运维与调试 | Ops | 调度、评测、路由调试、检索调试 |

### 3.3 明确不做（本轮）

- 不删除次要路由与页面  
- 不把 Seekstone 接到产品 `/rag`  
- 不在中文 UI 为「专业感」保留 Agent / RAG / MCP 字样

## 四、知识库建设优先级（产品）

```text
P0  说清定位：资产知识为主，文档为辅；与 Seekstone 分家
P0  主路由 + 中文文案收敛（本文件第三节）
P0  知识库按任务重做 UI + 独立监控预警台取消（见 kb-and-monitor-ux-plan.md）
P1  资产索引闭环可运营（覆盖率、过期、自动重建体验）
P1  对话/工作流侧检索消费质量与评测指标
P2  通用文档库治理（权限、多库、引用溯源）— 第二曲线
```
