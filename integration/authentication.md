# 认证方式

不同场景使用不同凭证。

## 三种凭证

| 场景 | 凭证 | 传递方式 |
|---|---|---|
| 界面操作 | 登录态 | 平台自动处理 |
| 外部系统调用多个工作流 | 用户 API Key | `X-API-Key` |
| 只开放一个工作流 | 工作流 Key | `X-Workflow-Key` |

## 用户 API Key

适合你自己的脚本或系统需要调用多个已发布工作流。

1. 在平台中创建 API Key。
2. 保存密钥，平台不会再次完整显示。
3. 调用接口时放在请求头中：

```http
X-API-Key: sk_xxxxxxxx
```

## 工作流 Key

适合只把某一个工作流开放给外部系统。

1. 发布工作流时生成工作流 Key。
2. 只把密钥交给需要调用这个工作流的系统。
3. 调用接口时放在请求头中：

```http
X-Workflow-Key: wf_xxxxxxxx
```

如果密钥可能泄露，可以在设计器中重新生成，旧密钥会立即失效。

## 怎么选

| 情况 | 推荐 |
|---|---|
| 你要调用自己有权限的多个工作流 | 用户 API Key |
| 你只想开放一个工作流 | 工作流 Key |
| 你在平台页面里操作 | 不需要手动处理认证 |

## 安全建议

- 不要把密钥写死在前端代码里。
- 不要把密钥提交到 Git。
- 外部回调要验证签名。
- 密钥泄露后立即轮换。
